# Economy: next five decision gates

These are completion conditions, not a claim that all diagnostics or fixes are
finished. No new run should be requested solely because a test elapsed: inspect
coverage first. Preserve protected Core, unrelated changes, saves and old logs.

## 1. Close the accounting evidence gaps

Join workshop cash, procurement receipts, cargo snapshots and remaining cost
basis. Trace livestock/wool production through competing consumption. Attribute
battle money to allocations and naval payments to valuation and asset lifecycle.
Keep unknown cash sources and unavailable endpoints explicit.

Exit: the combined report can distinguish a proven loss/creation of money or
cargo from a missing observation. Current gaps include complete procurement
joins, naval destruction/player-penalty evidence and competing-demand coverage.

## 2. Prove diagnostics before asking for gameplay

Run isolated Release builds and native-target fixtures, plus corrupted, missing,
duplicate and nested receipt cases. Cover normal reload, rollover, interrupted
capture, rollback and optional-module absence. Include all required checks in
the candidate verification route, with no private-test security scan.

Exit: failures are visible; a missing event cannot count as a pass. Fixture
results are not represented as live economy validation.

## 3. Prepare one combined acceptance run

Bind the test plan to exact candidate hashes and enabled modules. List required
events before deployment: dispatch, arrival, consume, return/liquidate, successful
and denied production, workshop expenses, battle reward and naval recovery when
enabled. Capture day intervals, profitability/capital/town cash, reconciliation
and event counts together. Include the diagnostics lifecycle checks.

Exit: report which paths were exercised and which were not. Fifteen or thirty
days alone does not guarantee rare events. A 30-day rolling file overwrites its
own previous period, so preserve evidence before rollover when needed. Deployment
and a game run still require authorization; never restart the game automatically.

## 4. Apply only demonstrated corrections

Use matched cash/cargo evidence to identify the owning subsystem. Fix rate or
transfer defects there; reassess wine, smithy and linen profitability afterward.
Do not infer an income multiplier from the historical 28.19-million increase
without matching transaction evidence. Keep configurable policy separate from
diagnostic observation and retain save compatibility.

Exit: a reproducible failing case passes after the smallest correction, and
adjacent supply, pricing, money and optional-logistics contracts still pass.

## 5. Validate release and subsequent operation

Compare acceptance evidence with the pre-fix baseline using equivalent coverage,
not different cohorts or aggregate gross reward scopes. Verify install/update,
optional dependencies, reload, uninstall/rollback documentation and production
versus diagnostics separation. State actual framework authority and remaining
scope. Run the public release/security gate only for the release candidate.

Exit: separate build correctness, economic evidence and live acceptance in the
release report. Any untested path stays a named limitation; do not label it 10/10.
